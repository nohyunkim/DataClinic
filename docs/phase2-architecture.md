# DataClinic — Phase 2. 기술 아키텍처 설계

- 문서 상태: **기본 방향 확정** (세부 정책·성능 수치는 구현 전후 검증)
- 결정일: 2026-11-22
- 관련 문서: `docs/phase1-planning.md`

## 1. 결론

**MVP는 별도 백엔드 없이 브라우저에서 CSV를 분석·정제하는 Local-first 정적 웹앱**으로 구성한다.

- 브라우저: React + TypeScript + Vite
- 스타일: Tailwind CSS, 아이콘: Lucide
- CSV 파싱: Papa Parse 및 필요한 브라우저 인코딩 기능
- 데이터 진단·정제: TypeScript 모듈
- 차트: 필요할 때 Recharts
- 테스트: Vitest + React Testing Library
- 배포 1순위 후보: Cloudflare Pages (실제 배포 전에 무료 플랜 정책 재확인)
- Python/Pandas: 필요 시 브라우저 처리 결과를 검증하는 **별도 테스트·검증 스크립트** 용도; 필수 서비스 백엔드 아님

## 2. 아키텍처 비교와 선택 근거

| 기준 | A. 브라우저 처리 | B. FastAPI + Pandas 서버 | C. 브라우저 + 독립 Python 엔진 |
| --- | --- | --- | --- |
| 무료 운영 | 유리 | 서버 무료 한도 및 정책 의존 | 웹앱만 배포 시 유리하지만 운영·관리 분리 필요 |
| CSV의 서버 전송 최소화 | 가능 | 서버 전송 필요 | 구성 방식에 따라 다름 |
| 개발·배포 복잡도 | 상대적으로 낮음 | 프론트·백엔드 모두 관리 | 두 처리 경로의 일관성 관리 필요 |
| Python 활용 증명 | 별도 검증 코드로 보완 | 직접적 | 직접적 |
| 초기 MVP 완성 가능성 | **가장 높음** | 중간 | 상대적으로 낮음 |

5MB 안팎의 CSV에 필요한 결측·완전 중복·기본 통계·정제는 TypeScript로 구현 가능한 범위다. 실제 처리 시간과 메모리 적합성은 대표 데이터셋으로 측정하며, 검증 전에 성능을 보장하지 않는다.

## 3. 논리적 데이터 흐름

```text
사용자 CSV 선택
  ↓
파일 검증 (확장자만 신뢰하지 않음, 크기·내용·오류 확인)
  ↓
인코딩 확인 및 CSV 파싱
  ↓
원본 스냅샷 보관 (불변)
  ├── 구조 및 품질 진단 → 문제 위치·진단 결과 표시
  └── 작업 데이터 복사본 생성
          ↓
     정제 방법 선택
          ↓
     적용 조건 검사 + 변경 예상 영향 미리보기
          ↓ (사용자 명시적 실행)
     작업 데이터에 정제 반영
          ↓
     원본 vs 작업 데이터 비교
          ↓
     안전성 검사 및 CSV 다운로드
```

실제 업로드 데이터는 서버·데이터베이스에 영구 보관하지 않는다. 초기에는 브라우저 메모리에 두며 새로고침 시 파일을 다시 선택하도록 한다.

## 4. 화면·기능 모듈 경계 (구현 전 설계안)

- `file`: 파일 검사, 인코딩, CSV 파싱, 예시 파일 불러오기
- `data`: 파싱 결과 모델, 컬럼 메타데이터, 자료형 추론, 결측 판정 규칙
- `diagnosis`: 결측·중복 탐지, 숫자형 기본 통계, 선택적 IQR 후보
- `cleaning`: 정제 방법 검증, 영향 미리보기, 사용자 승인 후 실행
- `comparison`: 원본과 작업 데이터의 수치 비교
- `export`: CSV 내보내기, BOM 옵션, 수식 실행 위험 대응
- `ui`: 랜딩, 데이터 작업 공간, 정제 패널, 진행 단계, 상태·오류 피드백

이름은 논리적 책임을 설명하기 위한 것으로, 실제 디렉터리 구조는 Phase 4 초기 구현 시 확정한다. 과도한 추상화는 지양한다.

## 5. 데이터 모델·계산 원칙

### 원본과 작업본

- 원본 데이터와 작업 데이터의 상태를 분리한다.
- 데이터 정제는 원본을 직접 변경하지 않는다.
- 정제 실행 버튼을 누르기 전에는 실제 작업 데이터에 변경을 적용하지 않는다.
- 정제 전 예상 영향은 실행과 같은 규칙으로 계산하되 미리보기 때문에 상태가 변하지 않게 한다.

### 결측치·중복·자료형

- 기본 결측 정의는 비어 있는 CSV 셀을 기준으로 시작한다. 공백, `NULL`, `N/A` 등의 특별 취급은 실제 사례를 검토해 명시적으로 정의한다.
- 결측 **셀 수**와 결측이 있는 **행 수**는 별도 지표로 표시한다.
- 완전 중복은 모든 컬럼의 값을 기준으로 행이 동일한 경우로 정의한다. 동일 키만 가진 서로 다른 행은 자동 중복 처리하지 않는다.
- 자료형은 추론 결과임을 명시하며, 혼합 자료형과 빈 컬럼 등 예외를 테스트한다.
- 평균·중앙값은 적절한 숫자형 컬럼에만 제공한다. 최빈값 대체도 적용 가능 여부를 검사한다.
- IQR 이상치는 **오류가 아닌 후보**로 표시하고, MVP-1에서 제거·수정하지 않는다.

## 6. 파일·인코딩·성능 정책

| 항목 | 초기 정책 | 검증할 사항 |
| --- | --- | --- |
| 파일 크기 | 약 5MB 제한부터 시작 | 실제 브라우저 메모리 및 응답성 |
| 형식 | CSV 중심, 확장자 외 내용·파싱 결과 확인 | 빈 파일, 잘못된 구분자, 인용부호 오류 |
| 문자 인코딩 | UTF-8 기본, UTF-8 BOM 및 CP949 처리 검토 | 한국어 깨짐 여부와 사용자 재선택 경로 |
| 표 렌더링 | 페이지 처리 또는 필요한 행만 표시 | 행·열 증가 시 성능과 탐색성 |
| 긴 처리 | Web Worker 도입 필요성 측정 후 결정 | 메인 스레드 멈춤 여부 |
| 지속성 | 영구 저장 없이 브라우저 메모리 | 새로고침 시 상태 초기화 안내 |

차트는 데이터 테이블을 방해하지 않는 범위에서만 제공한다. 무거운 라이브러리(DuckDB-Wasm 등)는 실제 필요가 확인되기 전까지 추가하지 않는다.

## 7. 보안·개인정보 처리 원칙

- 업로드 CSV를 원격 API로 전송하지 않으며 개발·운영 로그에 원본 값을 기록하지 않는다.
- `.env`, 로컬 데이터베이스, 실제 고객 데이터, 샘플이 아닌 개인정보 CSV는 Git 추적에서 제외·점검한다.
- `.gitignore`는 **이미 추적된 비밀값을 제거하지 않는다**. 커밋 전 변경 파일을 확인한다.
- CSV Formula Injection 위험 셀에 대한 내보내기 정책을 정하고 테스트한다. 값 보존과 스프레드시트 안전성의 트레이드오프를 설명한다.
- 정제 결과 다운로드 시 UTF-8 BOM 옵션을 제공하고 Windows Excel 호환성을 확인한다.
- 악의적이거나 비정상적인 CSV 입력, 과도한 행·컬럼, 예상 밖 인코딩에 대해 오류 메시지와 제한을 제공한다.

## 8. 테스트 전략

### 로직 단위 테스트 (Vitest)

- 정상 CSV, 빈 파일, 잘못된 CSV, 한글 컬럼, UTF-8 BOM/CP949, 혼합 자료형
- 결측치, 완전 중복, 모든 값이 결측인 컬럼, 숫자형 통계, IQR=0(기능 도입 시)
- 결측 행 삭제, 평균/중앙값/최빈값 대체, 중복 제거
- 정제 후 데이터가 0행이 되는 경우, 원본 불변 확인
- 예상 영향 미리보기와 실제 적용 결과의 일치
- CSV 내보내기 및 Formula Injection 방어

### UI 테스트 (React Testing Library)

- 업로드 전/중/완료, 분석 중/성공/실패, 결과 없음
- 컬럼 선택과 문제 위치 탐색
- 자료형에 맞지 않는 정제 방법 비활성화
- 정제 전 확인과 실행 상태 표시
- 정제 전후 비교 및 다운로드 가능 상태

### 별도 검증

Pandas 기반 검증 스크립트는 **선택적**으로 작성해 진단 결과와 정제 계산을 교차 검증한다. 5MB 샘플 기준 실제 처리 시간, UI 응답성, 메모리 사용을 측정하고 결과를 기록한다. 목표 성능은 측정 후 확정한다.

## 9. 배포·저장소 관리

- 정적 웹앱으로 무료 배포하며 **Cloudflare Pages**를 1순위 후보로 둔다.
- GitHub 저장소와 배포를 연동한다. 배포 직전 사용량 한도·정책·설정·도메인을 공식 문서에서 재확인한다.
- GitHub 작업은 의미 있는 단위로 Issue → 작업 브랜치 → Commit/Push → PR → 검토·Merge 순서로 운영한다.
- 기능 개발 전 Phase 3에서 선택한 **A(Data Workspace) + C(Guided Data Studio)** 디자인의 상세 명세를 확정한다.
- README는 **Phase 7**에서 최종 기능·테스트·배포 결과를 반영해 작성한다.

## 10. 확정·후속 검토 사항

**확정:** 브라우저 중심 Local-first, React/TypeScript/Vite, 기본 TypeScript 분석 엔진, 원본 불변, 별도 필수 서버 없음, 초기 영구 저장 없음, 배포 1순위 Cloudflare Pages.

**세부 검토:** 인코딩 선택 UX, 구체적인 결측 정의, Worker 필요성, 5MB 실제 처리 한계, 다운로드 시 수식 방어 방식, UI 상태·에러 문구, 무료 호스팅 정책.
